# FINAL PROPOSAL — SAPR-RAG (State-Aware Process Rewards as State-Conditioned Progress / Q Modeling)

**Working title**: *State-Conditioned Action-Value Modeling for Repairing Agentic RAG Trajectories*

## 0) One-paragraph abstract
Agentic RAG pipelines fail on complex QA not because retrieval is impossible, but because the **trajectory control** is brittle: subqueries drift or repeat, bridge entities are dropped, noisy evidence is chosen, intermediate claims become unsupported, and the system stops too early (or keeps searching after evidence is sufficient). We propose **SAPR-RAG**, a lightweight critic layer that models **state-conditioned progress and action-values** for the key controllable actions in Agentic RAG—**query selection**, **evidence selection**, and **stop decisions**—and uses these estimates to repair trajectories online under a **fixed compute/retrieval budget**. The core thesis is that progress-style value modeling over explicit trajectory state yields consistent improvements beyond static reranking and monolithic step PRMs, while remaining simpler than online RL/MCTS.

## 1) Problem anchor
**Problem**: In multi-step retrieval reasoning, the “right next action” depends on what has already been retrieved/used. Static scores (retriever scores, query-doc reranker relevance) and generic step PRMs often fail to reflect **marginal utility under the current state**, leading to error propagation across steps.

**Constraints (project)**:
- Baseline: **ReasonRAG-LoRA** (kept fixed as the policy backbone).
- Datasets: **HotpotQA / 2Wiki / MuSiQue / Bamboogle**.
- No large-scale GRPO before small-scale verification.

## 2) Key idea: state-conditioned progress and action-value modeling
We model Agentic RAG as a trajectory of states and actions.

### 2.1 State
At step *t*, the state `s_t` contains:
- original question `q0`
- step index and remaining budget (steps, retrieval calls)
- history of subqueries `q_1…q_{t-1}`
- history of retrieved docs and selected evidence `E_{<t}`
- current intermediate answer / claim (optional)
- optional compact “gap” summary: what information is still missing

### 2.2 Actions
We focus on three action families:
1) **Query action** `a^q_t`: select / rewrite the next subquery from candidates generated by the frozen ReasonRAG policy.
2) **Evidence action** `a^e_t`: select a subset (e.g., top-m) evidence from retrieved top-k docs.
3) **Stop action** `a^s_t`: decide to stop (answer now) vs continue retrieving.

### 2.3 Progress / value targets
Define an implicit progress value:
- `V(s_t)` ≈ expected probability that the final answer will be correct **and evidence-supported**, given remaining budget.

For each action type, define an action-value:
- `Q_x(s_t, a_t^x)` ≈ expected `V(s_{t+1})` after taking action `a_t^x`, where `x ∈ {q,e,s}`.

SAPR-RAG does **not** require online RL; it only needs a **ranking signal** over candidate actions conditioned on state.

## 3) Training (offline, small-scale first)
### 3.1 Data
- Run ReasonRAG-LoRA to produce trajectories.
- At each step, sample *C* candidate subqueries (from the same generator) and retrieve top-k docs (same retriever).
- Construct candidate evidence subsets and stop/continue alternatives.

### 3.2 Labels with minimal leakage
Hierarchy of supervision:
1) **Dataset evidence supervision** when available (HotpotQA/2Wiki supporting-fact coverage; gold-doc recall).
2) **Outcome labels** (final EM/F1 on dev) used only offline.
3) **LLM-judge distillation** (V0) to create pairwise preferences over actions from state-only context (no gold shown), later distilled into smaller critics.

### 3.3 Objective
Learn to rank candidate actions given state:
- pairwise preference learning for `Q_x(s,a)` (DPO/BT-style), or
- regression to a progress proxy `\hat{\Delta V}`.

## 4) Inference-time repair under fixed budget
Wrap the frozen ReasonRAG policy:
1) generate candidate subqueries (same count as baselines)
2) choose `a^q_t = argmax Q_q(s_t, a)`
3) retrieve top-k docs
4) choose evidence subset by `Q_e(s_t, a)` (or per-doc marginal utility)
5) choose stop vs continue by `Q_s(s_t, stop)` vs `Q_s(s_t, continue)`
6) trigger repair when expected progress is low (rewrite query / rerank evidence / continue)

**Compute matching**: retrieval calls, candidate counts, and tokens are fixed across systems.

## 5) Publishable core claim
> Under matched compute, state-conditioned action-value modeling over explicit trajectory state yields consistent gains for a fixed ReasonRAG-LoRA backbone on complex QA, outperforming static rerankers and monolithic step PRMs by reducing query drift/repetition, improving marginal evidence utility, and correcting premature stopping.

## 6) Novelty positioning (tight)
| Related line | What it covers | SAPR-RAG’s distinction |
|---|---|---|
| ReasonRAG | process rewards for steps | SAPR reframes rewards as **state-conditioned progress/Q** with modular heads + explicit state ablations + compute-matched repair |
| DecEx-RAG | MDP decomposition/execution | SAPR targets retrieval-reasoning control and is a plug-in critic wrapper |
| HiPRAG | over/under-search control | SAPR unifies query/evidence/stop value modeling; stop is one head |
| ProRAG | learned PRM + search/RL | SAPR aims for offline modular critics; shows state features matter without online RL |
| DPA-RAG-style rerankers | doc preference reranking | SAPR uses **state-conditioned marginal utility** and also models query/stop actions |

## 7) Explicit non-goals (to protect the paper story)
- No large-scale GRPO before small-scale verification.
- Prompt judges are bootstrapping only.
- No gains from extra retrieval/tokens.
